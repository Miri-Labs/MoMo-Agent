# 波形预备、系统事项卡片与历史录音整理

本轮基于 `3503819`，交付版本为 `1.1.0`。用户要求同时处理波形打开慢、系统事项卡片层级、历史录音长期等待整理三个问题。卡片按本轮明确要求使用少量颜色，沿用系统字体与既有 MoMo。

## 历史录音为何一直等待

从已连接手机只读复制资料库进行检查：SQLite 完整性检查通过；1,364 个分片任务待处理、136 个完成；25 轮录音仅有 5 份结束回执。没有活动的处理 attempt。原始资料库仅放在忽略目录，不随代码提交。

存在三个互相放大的问题：分析任务先校验、持有后面整轮原音；文字识别的顺序解码器也重复持有剩余整轮；连续说话缺少自然停顿时，分析可能长时间不发布检查点。缺少结束回执的短尾段又会一直等待更多输入。

现在分析和顺序解码只获取接下来的约两分钟输入，保留完整分片边界和当前识别窗口需要的上下文。连续讲话达到约 64 秒模型音频后，在完整识别核心边界发布检查点，未完成的核心留到下一轮。资源释放仍由归档层的 lease 与取消屏障管理。

自动处理可以封口超过 30 分钟的已收到快照；用户明确重试时立即处理选中的已收到范围。这不写入 `epoch_closures`，不伪造手表停止事件，也不宣布未知尾部已完整。迟到音频继续从保存的检查点处理，真正的结束事件仍按原协议接收。

每日列表与进度从归档 actor 的同一快照取得：分母为当天实际接收的音频范围，分子为识别完成与确认无人声范围的并集，跨午夜按帧裁切，不重复计算。缺失待同步和原音不可用另行显示。缺少结束回执不会阻塞现有文字或回听；不估算无法保证的剩余时间，也不将尚未接收的未知尾部计入 100%。

## 波形提前准备

原路径在打开播放器时才解码；缓存命中也先完整校验原音。现在接收录音后和进入前台时由单个低优先级任务准备波形，优先可见时间线范围和新收到的分片，再分页处理旧音频。后台时取消，恢复后继续。接收回执不等待波形。

每个分片范围保存 256 个 RMS 值，二进制约 1 KB；内存上限 64 条，磁盘约 16 MiB，批量修剪。缓存命中只校验来源、清单与文件身份，避免反复扫描原音；真正播放、定位、恢复播放仍完整校验音频哈希。文件变化、删除、代次与引用失效继续使缓存不可用。聊天引用只读取其涉及分片的元数据。

播放器去掉生成波形进度条、旋转指示与“暂无可用波形”等等待文案。可选缓存尚未准备时显示安静的点状刻度，播放不依赖它。首次处理旧缓存仍需要解码，不能承诺所有历史音频首次打开均已准备完成。

## 系统事项卡片

闹钟、待办、日程分别使用平面淡橙、淡绿、淡紫，深色模式使用对应暗底。卡片突出标题与时间，使用矢量图标、整卡点击和轻微按压反馈；减少动态效果时停用缩放。未设截止日期的待办不编造时间，“已添加”和“已完成”分别展示。

原生详情首先展示重新读取的系统内容，主操作为修改事项，记录、核对、撤销为次要信息。只有缺少当前资源时才明确显示“上次操作记录”。权限、重新核对、编辑 revision 与撤销的原有所有权不变。日期显示覆盖全天、时区与每周闹钟。
