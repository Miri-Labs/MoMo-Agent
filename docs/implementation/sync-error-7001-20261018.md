## 代码问题与修复

原实现仅按消息哈希退避。一条控制消息发生通道级错误后，协调器仍能从剩余上千条待办中提交其他消息；这些消息随后失败又释放名额，形成一轮密集提交。单条消息退避无法约束整条通道故障。

- 将通道级故障的退避放在两端共用的 `LinkControlSubmissionState`。通道冷却时，新控制消息返回 `deferred`，保留游标与持久待办；已有系统副本仍占用队列预算。同一批在途失败只增加一次通道退避。
- WatchConnectivity 的 `genericError`、`sessionNotActivated`、`sessionInactive`、`notReachable`、`deliveryFailed`、`transferTimedOut` 使用通道退避。按错误域和枚举判断；载荷错误等继续按单条消息处理。
- 沿用 30、60、120、240、300 秒的退避上限。旧批次迟到的成功不能提前解除冷却；冷却后后台发送成功再恢复短间隔。文件队列与录音准入不受控制通道冷却影响。
- 即时副本收到 `control_preserved=true` 后，记录对端持久收件箱确认，并通知协调器恢复对应的传输状态。同一消息的后台副本之后失败，不能再次恢复其错误或退避；其他消息的失败继续保留。
- 收件箱确认不等于 `ReceiptApplied`。手机仍保留录音回执待办，手表仍须成功应用回执后才能按原规则清理原音。原有跨重启应用确认校验继续保留。
- 新增安全诊断日志仅记录消息类型、错误域、错误码、最终传输失败标记、可达状态和系统队列条数，不记录消息内容、身份、音频或转录文本。

本轮没有更改协议编码、数据库结构、删除授权及原音保留策略。没有新增跨异步调用持有的数据库事务或文件句柄。控制消息仍受 32 条和累计 16 KiB 的队列预算约束。
