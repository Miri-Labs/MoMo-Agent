# 摘要重复校验导致的手机发热

2026-10-20，用户报告手机发热严重。连接设备后，直接采集正在运行的 1.15.1 进程，没有为采样重启应用。

## 真机证据

- 两次约 20 秒的进程采样中，平均 CPU 占用分别为 43.3% 和 36.9%。Unix 系统调用分别增加约 217 万和 104 万次。
- 5 秒 Time Profiler 录制包含 2,621 个 CPU 样本。其中 1,487 个调用栈经过 `ArchiveStore.validateTimelineSummary`，1,548 个经过 `timelineDaySnapshot`。这些是包含子调用的计数，存在重叠，不能相加。
- 热点路径为 `TimelineModel.queueSummaries` → `cachedTimelineSummary` → `validateTimelineSummary` → 重建整天时间线。数据库查询、JSON 解码、文件存在性检查均在这条路径中。
- 同次录制的温度状态为 **Serious**。
- 两次转录诊断文件相同：已完成 107 个窗口，`nativeInFlight=false`，阶段为 `waitingForContext`。此次采样没有证据把持续负载归因于正在识别的 ASR。
- 同期也存在记忆整理工作。当前证据没有证明这些工作异常；本次没有关闭它们，也没有改变 VAD、转录、同步间隔或后台任务准入。

原始日志、trace 和导出调用栈保存在任务 worktree 的 `tmp_agent_output/20261020-thermal/`，未提交用户设备数据。

## 修复

1. 摘要缓存按日期和识别配置批量校验。一批中的同一天只读取一次权威时间线，再核对各条摘要的内容版本和来源。校验结果不跨调用保存。
2. 时间线页面一次提交待校验的摘要队列。后台写入新摘要后，只刷新对应日期。
3. 记忆整理完成、摘要缓存命中和空队列完成不再发送摘要刷新通知。
4. 单个损坏的可选缓存不会阻止同批其他有效摘要显示；错误仍记录到日志。旧格式迁移在来源和模型配置校验后执行。

修改、删除与模型配置变更仍使旧摘要失效。网络生成前后的来源校验继续保留。

## 验证

- `ActivityTimelineTests`：14 项通过，覆盖同日批量读取次数、转录版本变化和删除。
- `AutomaticInsightsTests`：23 项通过，覆盖缓存复用、损坏缓存隔离、新摘要通知、无变化时不通知，以及后台记忆任务继续执行。
- `TimelineModel` 的实际源码和新增页面队列用例在 macOS 测试宿主运行通过：同日两张卡片一次读取，更新该日期不会刷新另一日期。此项是模型层验证，不是 iPhone UI 自动化。
- 1.15.2 的 Release 构建、包内容检查和手机/手表包签名校验通过。手机已覆盖安装并启动。两次手表安装均在建立开发通道时超时，未完成手表更新。

## 安装后继续定位

1.15.2 安装后的采样不再以 `TimelineModel.queueSummaries` 的逐条缓存读取为主要热点。随后一次录制的温度状态为 **Fair**，但另一次 20 秒采样的平均 CPU 仍为 42.9%。期间发生了进程重新启动、ASR 模型准备和正常摘要生成，不能把这些采样直接当作同负载的降温对照，也不能据此宣布发热已解决。

安装前保存的 3,295 个分片 ID 在安装后均存在，另新增 30 个。诊断资料只保存在本地临时目录。

17:35:19，手机日志记录：

```text
Library refresh failed at 清理失效聊天引用: MoMoAgent.AgentError / 4
```

调用链为 `cleanupInvalidatedSessions` → `cleanHomeSuggestions` → `cachedHomeSuggestions` → `insightIdentity` → `AgentPromptStore.snapshot`。清理首页建议时借用了展示路径，后者会取得记忆文件锁。后台记忆写入持锁时，这条路径会抛出 `AgentError.busy`，阻止后面的失效聊天引用清理。

后续修复纳入 1.16.1：

- 清理首页建议只检查格式、语言、有效期和录音来源，不读取记忆快照。展示路径仍核对模型配置和记忆身份；来源失效仍按原规则处理；删除前仍确认文件未被并发更新。
- 每次记忆快照复用当前锁内已经读取的状态。`dream.json` 从读取、解析四次减少到一次，不增加跨调用缓存。
- 新增持有真实 `flock` 的回归用例：确认 `busy` 对应错误码 4；在锁占用时保留有效建议；修改来源后仍能移除无效建议、完成聊天引用清理并清空待清理队列。

这些改动保留后台记忆整理、转录和同步。94 项定向回归通过：14 项时间线测试，以及 80 项自动整理、记忆归档、记忆整理、提示词快照和聊天引用清理测试。真实持锁用例通过，确认日志中的错误码 4 对应 `AgentError.busy`。测试运行在 macOS，不代表手机后台任务已经完成真机验收。

1.16.1 已通过 Release 包与双端签名校验，推到 main 并覆盖安装到手机。查询确认版本为 1.16.1，启动后同一进程持续存在；短时日志观察没有再次记录清理失败。安装前的 3,350 个分片全部保留，新增 6 个，资料库身份不变。手表开发通道的只读诊断仍以 `RemotePairingError / 1001` 超时，尚未完成腕上更新。

## 后台摘要重新入队与重试

1.16.1 的后续 20 秒采样平均 CPU 为 46.3%，当时转录诊断仍为模型准备阶段。另一次 5 秒调用栈的 1,074 个样本中，619 个经过后台摘要生成的来源校验，614 个经过整天时间线构建。手机队列保存了 511 条重试记录；其中包含历史记录，不能把它们算成 511 个当前待处理任务。采样仍不足以证明待机发热已消除。

代码检查发现，历史摘要的入队标识和失败重试键包含个人记忆身份。记忆变化会重新排入历史日期，也会使同一份录音内容使用新的重试键，绕过原来的退避时间。摘要生成的实际输入只有录音正文和模型配置，因此这种依赖没有必要。

1.16.2 的调整：

- 历史摘要按录音内容、格式和模型配置判断变化；个人记忆变化仍刷新首页建议，但不会重新排入已经完成的历史摘要。
- 摘要失败重试键不再包含个人记忆身份。记忆更新不会缩短同一摘要的等待时间。
- 构建时间线时明确告诉 Foundation 原音路径是文件，省掉拼接每个 URL 时额外查询文件类型的调用；原有文件存在性与来源校验保留。
- 自动摘要失败日志记录错误域和错误码，便于核对真实失败原因，不记录录音正文或模型输入。

40 项相关回归通过，包括两项新增边界测试：修改个人记忆后不重新排入已完成的历史日期；摘要失败后修改记忆，同一任务仍遵守原来的退避时间。原有修改来源、删除来源、模型配置和后台处理用例继续通过。1.16.2 的首次增量真机构建因 Xcode 生成的 VFS 文件缺失失败，随后使用当前任务的 DerivedData 执行 `xcodebuild clean` 后重建。

重建通过。1.16.2 的 Release 包检查、手机与手表签名校验以及内嵌/独立手表包一致性检查通过，源码 `75bb60f` 已推到 main。18:27 的手机安装返回 `CoreDeviceError / 4016`；同时 usbmux 找不到目标手机，两端开发通道均显示 `unavailable`。因此 1.16.2 尚未安装，手机最后确认的安装版本为 1.16.1，手表更新仍未完成。停止重复安装，保留已校验的冻结包。

待真机连接恢复后，需要核对 1.16.2 安装与启动、摘要失败的具体错误码，以及模型准备结束后的稳定负载。当前证据能确认已修复的触发条件和清理错误，不能证明所有发热或摘要失败原因均已消除。
