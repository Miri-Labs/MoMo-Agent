## 1.34.1 · 任务操作回到聊天

**源码复核结论（2026-10-25）：本版移除了任务操作按钮，但尚未对齐 Rakazo 的连续消息接续机制。下面的测试结果只证明已实现的链路，不代表 Rakazo 交互已经复刻。**

手机和桌面共用任务界面移除“补充”“取消任务”以及“补充这项任务 / 改聊别的”模式。输入框始终为“发消息给 MoMo”。任务区保留状态；真正需要用户授权或回答的问题继续显示对应确认，不把普通消息当作另一个任务的授权。

升级时保留旧草稿，丢弃草稿中旧版保存的任务选择，避免按钮消失后仍把下一条聊天偷偷投递到原任务。已有已投递消息与重试记录不改写。

Hermes 的产品插件增加 `conversation_task`，将查看、调整、停止接到已有的本机任务 API。模型根据当前用户消息理解意图，不增加关键词取消规则或第二套执行器。工具先查真实任务，校验 work/run/generation 后投递；同一轮的相同操作保持幂等，旧目标不退化为新执行。只连当前私有运行目录指定的 loopback API，禁用代理及重定向，不暴露凭据，也不提供批准权限的动作。新提示词要求指代不清时问清、区分请求接收与实际完成、不把询问进展当成取消授权。

### 我们当前真正的差异

`conversation_store.py:accept` 为每条无显式目标的消息建立独立 work/native_root，复制最近 40 条、24 KiB 的可见历史；`personal_agent.py:_admit_input` 为它启动独立执行。界面看起来是一条聊天，执行层仍按每条消息拆分。1.34.1 的 `conversation_task` 是我们后来添加的任务管理工具，并非 Rakazo 的普通消息接续实现，也不能代替接续。

因此应先修消息生命周期：普通聊天由一个连续的对话执行承接；正在忙时持久接收新消息、在安全边界交给同一 Agent；没来得及回答的消息进入续跑。后台工作独立执行和回报，等待授权不堵住聊天，真正的权限仍走独立确认。保持 Hermes 执行引擎，不因 Rakazo 使用 Pi 就换引擎。

需要先证明“连续发两条消息只显示一次用户输入、调整在原对话生效”“刚好结束时不漏消息”“待授权时新聊天正常回答且旧授权不被批准”“断线重发不重复执行”“后台完成后主 Agent 回报”这几条，再将其称为对齐完成。

用户随后明确选择：聊天交互按 Dots 方向做差异化，不采用 Rakazo 的停止小方块。手机、桌面聊天和悬浮交互均不提供任务补充/取消/停止按钮；执行中仍能正常发送消息，停止、调整和询问均在对话中表达。三点仅表示当前回复等待，必要授权保留独立确认。此为用户的产品选择，不是对 Dots 全部实际实现的断言。

本轮静态核对共用聊天组件、手机远程页、桌面聊天和悬浮组件：没有残留任务停止按钮。桌面设置中的“停止运行”控制整个 Mac 服务，不属于聊天任务操作；保留该管理能力。本次更新约定与方案，无需重新构建或安装。

本轮只完成源码复核并纠正实施记录，没有再修改或替换运行中的 App。
