# 日历与待办的工具选择

用户反馈手机回答「日历只读，不能修改」。核对运行配置，当前仅连接 momo_context、momo_recordings、momo_computer；手机日历同步确实只是前台快照。原 policy 的「工具不提供创建或修改日历、提醒事项的能力」没有限定到 read_phone_context，容易把接口限制扩展为助手整体能力限制。

本次限定快照只读的作用范围，在 policy、MCP 工具说明与来源返回 guidance 中一致表述。用户请求改日程时优先选择实际可用、已授权且连接到目标账户的日历写入工具；没有专用接口则尝试现有电脑操作 MCP。不能虚构工具、混用手机快照 ID、改错账户或把点击保存当成成功。需要核对目标、时区、重复事件范围及保存后的实时结果；只补问缺失信息。

没有新增日历写入 MCP、EventKit 权限或手机后台写入队列。现有电脑操作仍受控制权和系统权限约束，Mac 未登录相同日历账户时不能承诺能修改手机日历。本次不执行任何真实日程变更。

验证：test_runtime.py 18 项、test_prompt_context.py 6 项、test_phone_sources.py 10 项通过，最后一组使用已安装应用的内置 Python，包含真实 stdio MCP 的工具发现与读取。日历初版策略长度 3453 字符，小于现有 4000 字符注册上限。起初使用不含 aiohttp 的基础 Python 运行来源测试报依赖缺失，换用内置环境后通过。

这些检查验证安装规则、上下文与 MCP 读取契约，不验证模型必然选择正确工具或真实日历改写。未重打安装包、未重启或改写当前运行的 Agent；已安装版仍需后续更新才能加载新规则。对外版本维持 0.0.1。

## 待办与其他能力补充

用户进一步要求涵盖待办。将同一规则推广到实际可用的服务操作，补齐提醒事项的新建、修改、完成、恢复未完成、删除。核对账户和列表，保留未要求修改的字段，重复事项按用户指定范围操作。未完成快照中记录消失不能证明完成或删除；恢复操作要去实时服务的已完成列表定位。记忆、内部执行清单和 Agent 后台任务不能冒充系统提醒事项。

能力检查结果：

- 日历、提醒事项：现有同步接口只读；没有专用写入 MCP，按实际可用工具选择服务接口或电脑操作，不宣称新增接口已经实现。
- 记忆：沿用 Hermes 原生记忆修改工具；不作为系统待办写入的替代品。
- 文件：已有 terminal/file 工具，按用户请求执行和核验，不受手机资料只读限制。
- 健康、到访：仍是授权后的观测资料读取，本次没有引入写入或改写历史观测的能力。
- 其他服务：只使用当前实际连接且获授权的工具，不能因为产品支持 MCP 就声称某个账户或服务已接通。

补充后策略 3809 字符，仍在 4000 字符上限内；运行环境、提示词上下文、手机来源的 18 + 6 + 10 项测试再次全部通过，含真实 stdio MCP 读取。没有执行真实提醒事项写入，也未替换已安装应用或其运行配置。以上是规则修正和契约验证，不是新增连接器或端到端日历/待办验收。
