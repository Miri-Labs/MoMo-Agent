# 已确认录音的系统传输副本回收

## 真机证据

手机和手表均已安装 `1.8.6` 后，手机仍报告 7001。12:44 的手机原生日志记录了具体失败：发送 `receiverIdentity` 时返回 `WCErrorDomain/7001`，底层为 `com.apple.identityservices.error/200`，当时 `reachable=false`，系统尚有 22 条控制传输。200 的具体内部含义尚未确认。

新版手表的实时状态已到达手机，待确认片段从 974 降至 925；这只能说明确认队列有推进。最后一次手机资料库核对中，18 日仍未收到片段，不能据此宣布音频同步已恢复。这些数值来自上一轮真机检查，本轮需要重新读取两端队列。

## 本轮改动

代码检查发现：应用收到手机持久化回执后，只更新自己的发送状态，没有撤销系统里同一片段的旧发送副本。系统副本若迟迟不结束，仍占用四个发送名额；失败回调也会把已经确认保存的文件再次展示为失败。这是需要修复的状态处理缺口，是否为本次 18 日阻塞的直接原因仍以真机验证为准。

- 确认回执后撤销相同片段的系统发送副本。撤销不删除手表原音，不把系统传输完成当作持久化确认。
- 每次对账最多检查四个系统发送副本，按片段 ID 查询账本。进程重启后也能撤销已经有有效回执的旧副本，不扫描全部历史录音。
- 只采用状态为已确认或已清理、没有对账暂挂且未被删除的持久化回执。手机缺失原音、过期、冲突或更换资料库时，不借用旧回执撤销待恢复的传输。
- 已确认文件的迟到失败回调不再产生文件投递错误；没有有效回执的真实失败继续退避和重试。
- 手机处理控制传输回调时，在账本查询的 actor 切换之后重新核对同一条指令的持久化 Inbox 回复，避免较早的失败覆盖较晚的确认。其他指令的错误仍独立保留，不使用状态摘要代替指令确认。
- 手表保存 `file-queue-diagnostic.json`，每 30 秒最多更新一次，只包含连接标志、系统队列数量及最多四个片段的进度单位，不写入原音或转录正文。

此次改动不将状态摘要当作文件回执，也不扩大原音清理权限。7001 控制传输失败仍须独立验证，不能用本改动将其直接标记为已解决。

交付版本为 `1.9.1`，跟随本轮最新 main 的 `1.9.0` 基线。验证、安装与数据补传结果保存在 `tmp_agent_output/20261019-sync-retirement/`。
