# SenseVoice Core ML 识别后端

2026-10-18 更新：长录音复测发现反复编译与 ANE 编译失败，当前候选尚未通过性能和稳定性验收，见[后续复测](sensevoice-coreml-benchmark-20261018.md)。下文保留初轮实施与验证记录。

用户确认保留 Sherpa / Silero VAD，把 SenseVoice 识别迁到 FluidAudio 的 Core ML INT8 权重。基线为 `8804653`；本任务在独立 worktree 实施，不操作主线程的设备或 checkout。

## 实施决定

- 一份 `SpeechEngine`、原有两条执行队列、同一个 Archive 和协调器。识别接收已有的有界 16 kHz PCM，不再读取、解码录音文件。
- 使用固定提交的 FluidAudio，只启用 ASR/VAD 代码，关闭 TTS、Diarizer 和 NeMo 可选依赖。通过其公开 `SenseVoiceModels` 加载器加载固定 revision、逐文件校验的 Core ML INT8 模型。
- 应用明确选择 Core ML 识别；原有 Sherpa ASR 只作为测试、对照和模拟器的显式参考后端，不作为真机静默回退。正常运行只加载一份识别模型。
- 保留已有分析配置指纹、窗口 ID、帧范围和恢复点。新的识别模型与适配规则通过独立 `recognitionFingerprint` 写入每个识别结果；既有记录缺少该可选字段时仍能读取。切换执行后端不重新整理已完成窗口。
- FluidAudio 的文字接口不返回现有契约要求的 token 时间戳。因此在原有识别队列中调用其公开模型，按同一贪心 CTC 规则保留 token 与模型时间坐标，继续交回既有提交屏障。时间戳表示模型对齐，不能升级为精确逐字时间承诺。
- 预处理指定 CPU，识别模型允许 CPU/ANE。缺少 ANE、模型不兼容、非有限输出和取消均明确失败；不把空文本作为推理失败的替代结果。

### 速度实测与适用范围

同一台 Apple M4、SwiftPM Debug、同一段约 4.99 秒的模型上下文，各复用模型运行 3 次。Core ML 的 native 阶段包含 CPU 预处理、模型 prediction、CTC 解码和结果编码；Sherpa native 阶段为原有 C decode 路径。该数据用于端到端后端比较，不能当作同一算子的设备微基准。

| 指标 | Core ML INT8 | Sherpa CPU / 2 线程 |
| --- | ---: | ---: |
| 首次模型加载（Core ML 包含这次首次 ANE 专门化） | 114.96 秒 | 0.67 秒 |
| 复用后 native 耗时中位数 | 0.166 秒 | 0.100 秒 |
| 复用后整个转写调用中位数 | 0.179 秒 | 0.111 秒 |

本机短句未出现提速；不能把“已接入 Core ML”写成“性能优化验收通过”。首次设备专门化成本需要单独管理，已有缓存下的首次加载也仍需测量。是否改善手机全天录音的吞吐、温度和耗电，需要在同一 iPhone、相同音频、相同电源/温度条件下比较，分别记录首次准备、模型复用、整个队列吞吐、峰值内存和后台过期。

当前只在独立分支集成和验证，未安装设备，也未改动主线程的 checkout 或 main。

Core ML 第一次进入模型前，测试同步门原来的 10 秒等待不足，首轮四个断言失败；计时采样确认正在 ANE 专门化。后续只把测试中等待模型进入的期限设为 180 秒，native 返回同步门仍为 10 秒，未改变产品超时、取消或重试语义。最终整套 coordinator 用例通过。新建引擎时仍有明显加载成本，本轮不把跨实例缓存收益作为保证。

首轮 Release 链接因并行验证期间磁盘不足失败。测试完成后，在未删除缓存的情况下重试原构建通过；完整产物检查为 `release-bundle-final.json`。自动安全检查拒绝了递归清理两个本轮缓存目录的命令，缓存仍保留。六个开发工具的依赖锁已重新生成并核对相同 FluidAudio 固定提交。
