# 统一本地 ASR

版本：1.18.0。

SenseVoice 和 FunASR Nano 共用 sherpa-onnx 1.13.8 / ONNX Runtime 1.28.2。移除 FluidAudio 的包依赖、模型适配器及应用中的旧 Core ML 模型资源。手表的录音、同步周期和抬腕同步行为不变。

## 执行方式

| 场景 | 处理方式 |
| --- | --- |
| 默认 SenseVoice | 保持上游 INT8 ONNX 文件。Core ML EP 执行支持的静态子图，其他算子由 ORT 执行。 |
| 下载的 FunASR Nano | 保持上游 INT8 ONNX 文件。编码器使用 Core ML EP；embedding 和 LLM 使用同一 ORT 的 CPU provider，保留上游 KV cache。 |
| 归档录音 | SenseVoice 每次最多两个窗口。只合并同一录音 epoch、同一代数据、同一已接收快照中的待处理窗口。 |
| 输入框语音 | 单段识别，共用已加载的识别器；不等待凑批。当前正在执行的归档批次完成后即可识别。 |

Nano 发布的编码器固定 batch=1，因此逐窗执行并复用模型。不能将它描述为真正的张量 batch，也不能将 Core ML EP 描述为整张图都运行在 ANE。

流式分析会为较长的已接收录音合并相邻窗口。额外分析范围最多为一个识别窗口长度，短尾段直接发布；不等待未来音频，不增加同步间隔。内存只保留有限的 PCM 窗口。

每个结果仍独立校验和提交。取消、后台时间到期或删除录音时，会撤销该批所有未提交的任务；已提交的结果保留。批量原生解码失败后拆为单窗重试，避免一个坏窗口反复拖住相邻窗口。模型加载失败单独报告，不用拆批掩盖加载错误。

坏片段回归还发现：分析完成后原音失效，未完成的识别窗口会被当前录音尾段的「等待后续音频」状态掩盖。等待状态现在也检查未完成识别窗口所需的原音，明确返回原音不可用；同批的正常窗口继续提交。

模型和语言在识别开始时一起读取，避免切换期间混用新模型和旧语言。FunASR 不接受韩语设置；模型验证和加载成功后才保存选择。切换不触发历史重转录。

## 下载和构建

高级设置增加「ASR 模型」。FunASR 下载清单固定到上游 revision，六个文件总计 1,009,605,061 字节。下载按 HTTP Range 保存完整分块，暂停或进程退出后可继续。每个文件通过大小和 SHA256 校验后才允许启用。

首次构建按[语音依赖说明](../../Native/SpeechVendor/README.md)准备运行库与模型。[安装说明](../../install.md)和 CI 已加入相同步骤。运行库发行附件固定哈希，解压后再核对完整文件清单。

上游接口补丁仅调整 ORT session 配置和 Nano 各阶段的 provider；不改权重，不重新量化。空闲推理线程关闭忙等，Core ML 编译缓存按模型 revision 复用。补丁、来源和重建步骤均保存在 `Native/SpeechVendor/`。

原生模型测试不等于手机速度或能耗验收。此次没有安装到手机和手表，也没有证明一小时录音能在五分钟内完成。

准确率也不能据此宣称提升：上游 ONNX 对公开测试短句的整段输入会将「开放」识别为「开饭」；既有带 VAD 上下文的质量用例仍能识别为「开放」。双窗回归比较相同 ONNX 和相同输入的结果，不能替代真实录音的准确率评估。

SenseVoice 的动态形状 Core ML 子图和 Nano 的量化 LLM，在当前组合下出现 MIL 执行计划错误。当前分别通过静态子图限制和 CPU 阶段执行解决。设备上的实际加速比例、峰值内存、耗电及下载后的首次加载时间仍需真机测量。
