# 后台同步恢复与控制消息诊断

1.10.3 已在手机和手表安装，用户仍报告 7007。手机 18:39 的持久接收清单仍停在 18:12：10 月 15 日 236 片、16 日 729 片、17 日 726 片，18 日尚无已提交片段，待确认回执 1124 条。安装成功不能作为同步恢复的证据。

## 已确认的错误路径

- 历史 7007 来自手机向手表发送 `receipt` / `reconcileResponse` 的 `sendMessage` 即时路径。它表示调用时对端不可达；解锁不保证手表应用拥有执行机会，发送前的可达检查也不能保证异步投递时仍可达。
- 历史 7001 来自 `transferUserInfo` 的后台完成回调，底层错误为 `com.apple.identityservices.error/200`。公开资料不足以进一步判断账号、网络、配对或系统服务原因。
- 7012 既可能来自 SDK，也可能来自本应用的 25 秒回复截止时间。旧日志未区分这两个来源。
- Mac 到设备的 `RemotePairing/1001` 属于开发连接，不能直接当作 WatchConnectivity 错误的原因。

依据为本机 SDK、已有真机日志，以及 [Apple 即时消息说明](https://developer.apple.com/documentation/watchconnectivity/wcsession/sendmessage(_:replyhandler:errorhandler:))、[后台传输说明](https://developer.apple.com/videos/play/wwdc2021/10003/)。以下修复针对可构造的应用缺陷，不将其表述为本次 7007 的已证实底层原因。

## 1.10.4 的修改

- 手表在等待激活事件时也检查持久 Inbox 和账本，不让延迟到达的激活事件跳过本地待办。后台执行额度结束时，尚未核对或尚未发布的工作继续申请下一次机会。
- 手表后台通过 application context 发布绑定与队列摘要，同时直接回复状态请求。冷启动不启动麦克风、不恢复历史录音、不打开原音；队列数量和大小从已封口片段的账本元数据读取。正常重复 drain 每次额度只发布一次，绑定变化才失效重发。
- 手机的自动恢复包含控制 Inbox 和原音 Inbox。读取失败代表待办未知，不能当作零；调用者取消也把已落盘工作交给下一次恢复。
- 对账响应的重试以持久 request 和当前响应为准。迟到响应与当前响应都匹配本库拥有的 request、但消息 ID 不同时，只退役旧发送尝试；无需历史哈希记录，因此也能处理 1.10.3 已覆盖的响应。当前完整 payload 相同则重排；找不到 request、scope/hash 不符或同 ID 内容冲突时仍保留未知状态或原类型错误。退役不表示对端已收件，不改变当前响应的待发状态，也不授权清理原音。
- 两端在 `Library/Application Support/MoMoAgent/control-transfer-diagnostic.json` 保存最近 32 条控制投递结果。记录消息 ID、代际、通道、SDK 回调时激活/可达状态、错误码和底层错误码，区分本地截止时间、SDK 错误和迟到回复。文件不保存消息正文或音频，读取上限 64 KiB。

录音删除仍要求匹配当前接收资料库的正式 Receipt。应用状态、系统发送完成和诊断记录都不授权删除原音。
