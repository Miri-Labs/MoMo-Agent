# Hermes 原生记忆与手机资料

版本 1.21.0 / 95；只开发、提交和推送 `codex/hermes-app-20261021`。用户最新决定：本版够用即可，记忆机制全部用 Hermes；转录仍要用于记忆整理。手机旧实现已对照最新 `origin/main f047927e`。

## 三种数据各有职责

- 手机 Archive 保存录音、ASR 原文和原始时间；Mac context 保存带身份、版本、校验和的文字副本。手机保留采集器，不恢复 Pi。
- Hermes 同一个 home 的 `memories/MEMORY.md` / `USER.md` 是唯一长期记忆。使用上游 `memory` 的容量、匹配、锁和原子写入，以及 `session_search` 的会话回忆。MoMo 的 GET/forget 只是原生存储适配器。
- 原始资料不等于长期记忆。同步不调用模型；只有有变化的转录批次进入 Hermes。健康日摘要计划作为可查询资料，默认不逐条写入长期记忆。

之前的 MoMo 事实、证据表和独立 memory profile 不再进入当前产品链路。旧文件保留、不静默导入；旧客户端缓存和待发送编辑不会覆盖新的 Hermes 内容。原生记忆没有结构化来源日期，UI 不伪造日期、证据边和使用计数。

## 旧手机实现的真实频次

来源：`MemoryDreamBatch.swift`、`PiAgentHost+MemoryDream.swift`、`AgentPromptStore+Dream.swift`、`PiAgentHost.swift:memoryDreamSources`、`PhoneInsightsModel.swift`，均读取上述 main 固定提交。6 小时是既有记忆维护门槛，**不能解释成新转录必须等六小时**。

本版没有复制手机的抢占式空闲调度。每次只保留一个转录整理 run，用户聊天通过 Hermes 正常运行；不会中断用户任务。连续录音每次上传新版本会合并待处理版本，但已接纳任务仍可核对，避免同时启动多个整理者。

## 每次注入什么

自动整理输入：Hermes 原生当前 MEMORY/USER + 最多 24 个新增/改动原文片段 + 每段真实录音时间、固定版本引用、段内偏移 + 本批剩余数量。不是当天摘要，更不是整库转录。指代不清时用 `read_recording` 补读相邻/相关原文，分页固定版本；无法确认则跳过。不要把录音中的每个说话者都当用户，不把未定计划当承诺。

进度存在已有 jobs 表的 input 中，仅记录“哪段资料投递过”，不是记忆。只有 run 完成后才推进；同版本同段不再发给模型。长转录分批直到完整消费，不静默丢尾部。改动会再次进入整理，提示 Hermes 合并或修正已有内容。原生记忆写入与源版本更新不是跨库事务：任务期间的修订可能短暂留下旧文字，由后续批次修正；不伪称已有证据级自动撤销。

普通聊天：不等整库同步。1.28.0 起，通过 Hermes 原生 pre_llm_call 注入最近 24 小时的有限转录原文：最多 3 场、20 段，每场最多 12 段，每段 1200 UTF-8 字节，完整资料 JSON 不超过 10,000 字节，明确时间、版本、引用、范围与省略。Hermes 带入自身记忆，按问题继续检索会话和 MoMo 全文；健康数值仍不默认注入，当前链路未接通。用户明确引用某段录音时，手机只确保该来源的精确版本已交付，版本变化时停止发送并提示重新选择。预算参考旧 main ContextBuilder，使用原生插件接入，不迁入 Pi 上下文引擎。完整构成见 [产品 Prompt](hermes-product-prompt-20261023.md)。

自动转录 run 仅开放 `memory` 与只读 `momo_recordings` 工具集，关闭额外后台 review；与聊天用同一个 home，不另起一份记忆。转录不能授权终端、文件写入、发消息或控制电脑。语义提取质量仍依赖实际模型，合成测试只证明链路。

## 健康信息如何给 Mac：已设计，待接线

推荐链路：**iPhone HealthKit → 手机摘要采集器 → 现有带认证 HTTPS 同步 → Mac 本地资料缓存 → 本机 MCP `get_health_summary` → Hermes**。隧道只运送 HTTP；MCP 是 Mac 内部工具接口，不负责打洞，也不要求手机开一个常驻 MCP 服务。

旧 main 的 `PhoneHealthContext` 已有六类只读查询：心率的日均/最小/最大值、静息心率、睡眠、步数、活动能量、训练；有独立超时、部分失败、睡眠重叠去重。`HealthContextController.initialSummary` 默认最近 7 个当地自然日，显式工具最多 31 天。该读取器目前随旧 Pi 入口退出编译，需要恢复到独立数据采集模块；**当前 Hermes 分支尚未接入真实健康同步，不能声称 Mac 已能读用户健康数据。**

第一版只做最近 7 天日摘要，同步后按问题取用；不先做任意范围 RPC、手机常驻代理、原始逐心跳镜像或全来源插件平台。具体约定：

1. **授权**：独立“健康资料”开关，默认关闭；说明会同步到配对 Mac、在健康/健身相关问题中可能交给所选模型。只有用户主动操作才弹 HealthKit 权限页，自动同步不弹窗。恢复旧 UI 的授权能力，不继承旧 Pi 的外部共享同意。
2. **采集频次**：开启/回到前台/用户手动刷新时采集；前台自动采集至少隔 15 分钟。系统 HealthKit observer 通知作为后续优化，不能把后台唤醒当准时任务；本版不承诺锁屏实时心率。
3. **快照**：以 device + health + grant_generation 标识；单调递增 revision、完整 7 天窗口和摘要哈希。字段保留 from、before、timezone、observed_at、每项单位和 issues。相同内容不重复传，仍能区分最近尝试时间和最近成功数据时间。整窗替换自然处理 7 天内补录/删除，不做多写合并。
4. **读取**：MCP 返回覆盖范围、观测时间、接收时间、是否超出刷新目标、可用字段和局部错误；超出 7 天的请求明确返回未缓存范围，不装作完整。手机离线可读最后快照，不能说是实时状态；过期也不自动归零。
5. **未知**：HealthKit 不能区分拒绝读取与无数据。nil 表示未知，不是 0；锁屏和单项查询失败保留错误标签。新快照不能暗中沿用旧数值并标成最新。
6. **关闭**：手机停采集并持久排队撤销标记，Mac 收到后删除对应健康缓存并拒绝旧 generation。手机离线时提示“Mac 清理待送达”，不假称远端已删除。重新开启新 generation，旧上传不能复活已撤销数据。用户在系统里撤回单项读取权限无法被可靠识别，后续无数据快照清空该窗口相应字段，不能假报已知撤权。
7. **记忆**：日常心率和步数留在资料层；用户明确要求记住的健康习惯/目标才交给原生 memory。不开自动疾病/情绪推断；来源撤销不自动抹除聊天记录或已写入的记忆，需要明确的独立删除动作。

健康之外按能力逐项接：手机专属数据继续“原生 API → 有界资料快照 → Mac MCP”；Mac 本身就能读的日历、邮件等优先在 Mac 接，避免多造一个双向代理。本版不恢复手机 Agent，也不把系统写操作混进资料同步。

Apple 官方依据：[读取授权与锁屏边界](https://developer.apple.com/documentation/healthkit/protecting-user-privacy)、[Observer 查询](https://developer.apple.com/documentation/healthkit/hkobserverquery)。Observer 后台交付不能由模拟器验收；真实设备授权与后台行为留到用户可操作时验证。

## 删除与同步的当前语义

手机 10 秒前台循环上传发生变化的来源并读取记忆列表；这个循环不等于 10 秒调用一次 LLM。Mac 是 Hermes 记忆所在端，手机只缓存完整列表；分页过程中变化则下轮重读，旧缓存保留。删除需要 Mac 在线，直接调用原生精确条目删除；旧条目的删除重试不删掉新修订内容。原始录音和聊天记录仍保留，未来新证据可能再次产生相似记忆。

当前版本的技术取舍是小而可用：不增加 CRDT、事件溯源记忆库、双向合并、离线记忆编辑和永久语义删除系统。健康的 grant/revision 是资料接入协议，不成为第二套记忆机制。

## 本轮验证

Python 28 项覆盖来源回执/分页/版本、原生记忆适配、批次预算、UTF-8 全文不丢失、修订增量和重启去重。Swift 客户端 20 项；手机同步宿主测试 2 项覆盖普通聊天不等整库同步及删除失败不入离线队列。Mac Debug、手机 Release 与内嵌 Watch/Widget 静态审计另记录构建日志。

真实嵌入 Hermes + 本机 MCP + 合成模型 POC：转录自动进入 MEMORY.md、聊天读同一记忆、Mac 生成真实文件、重复提交不重跑、UI 删除直接更新原生记忆。没有使用真实手机、Watch 或真实模型评价提取质量。CuaDriver 已安装的前序 POC 仍待系统授权，本轮没有继续请求授权或声称实际操控 Mac 应用已通过。
