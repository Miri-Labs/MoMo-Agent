# 稀疏录音处理吞吐

用户目标：少量时间有人说话的一小时录音，在手机上取得执行机会后，五分钟内处理完已收到的范围。无线同步、系统等待和实际计算分别计时。五分钟对应整体 RTF ≤ 0.08333；不能用 ASR 单项速度代替完整流程。

## 代码核对

现有生产链路已经先运行 Silero VAD，再将语音核心及少量上下文送给 SenseVoice。每个核心最多 20 秒、两侧上下文各最多 300ms。静音仍要解码并经过 VAD，但不会整段送给 ASR。分析页有界，VAD 与 ASR 各一条串行队列；保留最多两份已准备 PCM，避免重新读取识别输入。VAD 一个线程，ASR 两个线程，模型实例复用。

本轮找到四个额外开销：

1. 每提交一个 ASR 窗口，就删除这条录音的全部搜索行，再插入所有旧句子。
2. 每提交一个窗口，就检查所有录音的派生文件，连无关录音也重复读取和投影。
3. 每提交一个窗口，就刷新资料库、请求总结、运行音频维护和发布设备状态。
4. 按录音时间排序正文时，读取并解码了所有录音的分片 manifest。

长录音的小窗口越多，第一项的数据库写入增长越快。旧代码连续追加 N 条正文，会插入 N(N+1)/2 行、删除 N(N−1)/2 行。这是按旧代码推导的操作次数，不是手机耗时测量。

## 采用的实践与实现

- **按变化更新搜索数据。** SQLite 官方展示了按新增、删除和修改维护搜索内容的方式。本轮沿用现有普通 SQLite 搜索表，仅在 ASR 追加时插入新 span。人工修订仍替换整条录音的搜索行。没有引入 FTS5、GRDB 或新依赖。[SQLite FTS5](https://www.sqlite.org/fts5.html#external_content_tables)
- **只处理本次变化的录音。** 转写后的文档投影传入 `sessionID`，避免每个窗口扫描整库。日常完整刷新仍负责外部文件修订与冲突核对，不绕过目标录音的文件保护。
- **排序也限定当前录音。** `orderedSpans` 使用既有 `chunks_session` 索引读取当前录音的分片，保留 epoch 与采样顺序，不再解码其他录音的 manifest。
- **合并可重复刷新。** 参考 GRDB 对观测范围和重复值的处理，处理中的资料刷新、总结请求、音频维护及设备状态发布最多每秒发起一次。首个完成窗口立即刷新；处理结束、暂停、失败等收尾立即刷新。转写状态和批次进度仍即时更新。[GRDB 观测与去重](https://github.com/groue/GRDB.swift/blob/master/Documentation/Combine.md)
- **保留语音范围与原始时间映射。** whisper.cpp 的官方 VAD 示例也将检测区间映射到原始音频。本轮不拼接删除原音、不改变 VAD 阈值，也不压缩原音来换取计算速度。[whisper.cpp VAD 示例](https://github.com/ggml-org/whisper.cpp/blob/master/examples/vad-speech-segments/speech.cpp)

Silero 官方说明单线程处理一个 30ms 以上的片段可低于 1ms，支持先检测语音、再运行昂贵识别的设计。这个数字不是 iPhone 的测试结果，不能直接据此承诺设备吞吐。[Silero 官方](https://github.com/snakers4/silero-vad#key-features)

保留每个完整转录版本：旧引用校验、历史快照和文件冲突恢复依赖它。此次减少搜索行重建与无关文件扫描，没有消除完整快照和目标录音文档本身随内容增长的开销。数据库写入仍在原事务内，attempt、generation、原音租约与取消屏障不变。

预览不再依赖搜索行的插入顺序。数据库版本 11 在 `sessions` 保存最多 160 字的 `transcript_preview`，和正文版本在同一事务更新，删除录音时一并清除。今天优先、昨天后补时，预览仍取当前文档的首段。升级从旧索引回填；列表读取不用解码完整正文。此迁移不改原音、正文快照或引用代次，旧版程序不能打开版本 11 数据库。

## 可观测性

手机使用现有 `SpeechDiagnostics` 输出 `SpeechPerformance` debug 日志，包含操作、结果、总耗时、排队、读取、哈希、原生 ASR、分析背压和处理帧数。协调器以 `TranscriptionPerformance` 记录提交与投影耗时。日志不含正文、音频、路径或用户标识。

分析的总耗时包含等待消费者继续读取的背压，不能把它全部算作 VAD 模型计算。前后台资格、低电量和热状态的暂停也要与模型速度区分。此轮没有新增高精度模型或 Core ML 执行路径。

## 验证

175 项档案回归通过，覆盖：连续追加 200 条正文只有 200 次搜索行插入、零删除；空识别保留旧搜索结果；写入失败时版本、预览和索引一起回滚且可重试；历史快照、旧引用、分页搜索、人工修订和重新打开数据库正常；定向投影不改动无关录音，完整核对仍能发现其外部修改。另补乱序识别的预览、旧库回填及迁移失败后的再次恢复。

生产协调器与真实模型的 5 项测试通过，其中流水线测试覆盖四种执行方式：并行分析、串行恢复、用户暂停和后台到期。还核对新收件优先、跨日无结束事件持续处理及刷新频率限制。

新增 `PhonePipelineReplay --sparse-hour`：一小时稀疏公开中文音频，无显式结束事件，通过真实协调器处理。用法、计时边界和输出字段见[回放工具](../../Tools/PhonePipelineReplay/README.md)。本轮输出位于 `tmp_agent_output/20261018-transcription-throughput/`。手机五分钟目标仍须在实际设备上测量；Mac 软件链路结果单独记录。

最终回放运行于 Mac M4、10 个逻辑 CPU、macOS 27.0，Swift 默认 Debug 构建。使用新建引擎，计时包含模型校验和加载；没有清除系统文件缓存。`sparse-hour-final/throughput.json` 的结果如下：

| 指标 | 结果 |
| --- | ---: |
| 已接收 / 已处理范围 | 3600 / 3600 秒 |
| 完整处理耗时 | 23.0074 秒 |
| RTF | 0.006391 |
| ASR 核心音频 | 263.4 秒，约占总时长 7.32% |
| ASR 原生识别耗时之和 | 6.0406 秒 |
| VAD 输入 / 音频转换范围 | 3600 / 3600 秒 |

每分钟的中文结果与固定预期一致，时间位置落在对应分钟，接收范围全部处理完成，epoch 没有明确结束信息。此夹具只有重复的干净语音与静音，不衡量环境噪声误检、腕部录音质量或手机热降频；也没有运行手机资料页和总结任务。该数字证明共享软件链路的处理能力，不是手机达到五分钟目标的验收结果，也不是受控的优化前后速度对照。
