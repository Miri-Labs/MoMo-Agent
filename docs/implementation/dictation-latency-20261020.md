# 语音输入排队与自动总结扫描修复

用户在 1.17.0 语音输入中遇到长时间“正在转成文字”，同时仍看到文字输入提示。修复从 1.17.2 提供，本轮手机最终交付版本为 1.17.3，包含 main 上的键盘收起与照片原尺寸修复。

## 语音输入

历史录音的 `prepareStream` 会在串行分析队列上等待消费方。语音输入原本也把 VAD 工作放入同一队列，即使它只有几秒，也可能一直排在这次等待之后。修复为独立的短语音分析队列及复用的 VAD 实例；识别仍使用原来的串行队列和已加载的 Core ML 模型，避免另开一套大型模型。正在执行的识别窗口仍需完成，不能强行中断原生调用。

语音面板现在替换文字输入框及其按钮。转文字超过 30 秒时退出等待并显示重试提示，取消对应的识别请求，保留原有文字草稿。迟到结果不能覆盖草稿或写进另一段会话。此超时是交互恢复措施，排队根因由独立分析队列解决。

## 发热复测发现的额外工作

[1.17.0 真机复测](install-117-thermal-20261020.md)记录了自动总结中的周期性时间线重建。原代码先读取和校验整天时间线，再检查每个总结的重试时间；重试尚未到期也会重复扫描。

现在保存每个待处理日期的最早重试时间，在读取时间线前检查。新文字、来源或模型配置变化会清除对应日期的等待时间。个人记忆变化继续刷新建议，不会让历史总结绕过等待。已有队列格式兼容，后台转录和记忆任务仍可运行。服务失败日志补充经过筛选的错误类别，不记录用户正文、凭据或服务返回内容。

19:40:34–19:42:34 的 115 个主进程样本平均 CPU 为 102.32%，峰值 240.02%，内存 394.16 → 165.03 MiB。CPU 可超过 100%，表示多核进程用量，不能理解为整机百分比。此时设备同步正在推进；从本轮初次安装前到复测末尾，接收清单由 3,397 段增至 3,440 段，没有缺少原有条目。另一个诊断记录显示 VAD 在恢复处理中读取了 2,880 万帧，约 30 分钟音频，其中多数为回放分析。因此该采样不能与较早静置样本直接计算改善百分比。

## 1.17.3 同步刷新补充

增量同步和转录完成回调调用 `refresh(reconcileFiles: false)` 时，只清理已失效的聊天，不再顺带扫描所有总结缓存。完整资料核对仍执行缓存清理。缓存展示入口仍验证来源；延后物理删除不能让过时总结重新显示。写入转录投影前的文件冲突检查保留，避免覆盖用户编辑。

新增回归用例验证：连续增量清理不重建时间线；来源修改后仍删除失效聊天；旧总结不能读取；完整清理最终移除旧缓存。

自动整理回归最终为 27 项通过，加上 4 项语音模型/分窗测试和 6 项语音状态测试，共 37 项相关测试通过。1.17.3 Release 构建、两端签名、版本及内嵌 Watch 包一致性检查通过。对应源码为 `3155a74`，已推送 main。

手机 1.17.3 覆盖安装、版本查询和启动均成功。手表 1.17.2 的安装服务此前已返回成功；追加安装 1.17.3 时，开发隧道再次返回 RemotePairing 1001，尚未确认腕上 1.17.3 安装及启动。

1.17.3 首段资源采样在 19:49:57 因开发连接断开而结束。仅取得启动后约 20 秒数据，不能据此确认持续发热已经改善，也不能与 1.17.2 同步过程中的两分钟采样直接比较。

连接恢复后补采 19:54:04–19:55:04，取得 59 个样本：平均 CPU 22.49%，峰值 96.59%，内存 26.63 → 26.58 MiB。此时进程 PID 已变化，重启原因未核实，处理量也与前次不同，不能作为受控性能对比。

随后 15 秒调用栈记录系统温度等级仍为 Fair。374 个 CPU 样本中，同步自动恢复的 `PhoneReceiveCoordinator.reconcile` 命中 340 次，`ArchiveStore.refreshReconcileResponse` 命中 276 次，录音文件路径校验命中 242 次。这次未命中整批总结缓存清理。同步恢复中的文件校验是剩余主要开销；本轮没有确认其重复工作是否必要，也未验证持续空闲温度恢复。当前结论是语音阻塞和两处额外扫描已修复，发热仍有待验证。
