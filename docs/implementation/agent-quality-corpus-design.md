## Archive 状态如何落地

所有音频为明确标记的合成 fixture，本文验证 Agent 对正式状态的处理，不将人工转录或人工分析覆盖计作真实 ASR 质量。

| 状态 | 正式入口及 API 前检查 |
| --- | --- |
| ready | 真实 PCM 分片和 Manifest → `commitReceivedChunk` → `claimAnalysisJob` → `commitTranscript` → `projectPendingDocuments`；记录 version、generation、span 和 hash。 |
| pending | 仅正式收件；不 claim / commit，不创建伪正文或 SourceReference；`recordings` 为 pending、无全文，`contextStatus.pendingAnalysisCount` 与预期一致。 |
| partial | 同一 writer / session 的连续两片都收件，只提交第一片正文；第二片保持 pending。读取真实来源映射，证明已就绪片和待处理片不同，不能靠两段文字声称“部分”。 |
| failed | 正式 claim 后 `failAnalysis(retryable: false)`；检查 `.failed` 且不能读出不存在的正文，失败码不携带隐藏事实。 |
| noSpeech | 正式关闭 epoch / claim epoch analysis，再 `commitAnalysisBatch` 提交完整 `analyzedCoverage` 与 `noSpeechCoverage`，无窗口；检查 `.noSpeech`。这是明确标识的合成分析结果。 |
| completedWithoutText | 正式 `commitTranscript(spans: [])`，检查 `.completedWithoutText`，没有 noSpeechCoverage；不得误写成 noSpeech。 |
| revised | 已保存正文通过 `reviseTranscript(expectedVersion: …)` 修订；保存前后身份与当前状态，但只把当前文本交给新请求。 |
| deleted | 已建记录通过 `deleteSession` 及正常清理入口删除；检查 generation / tombstone 和不可读取，不直接操作数据库。 |

现有 `addTranscript` 会默认领取按时间排序的下一份 job。新增准备器必须先提交所有需要 ready 的片，再加入纯 pending / failed 的干扰片，或显式核对领取的 chunkID；不能让待转写样本被后续 ready 样本的 helper 意外消费。部分就绪必须让前片完整完成、后片保持 pending。所有预检在第一次收费请求之前结束，预检失败直接失败且零模型 admission。

Agent 只能对生产上下文和工具实际可见的状态作答。事实表不能要求模型知道尚未通过正式工具暴露的内部错误原因；若当前工具只能报告“未生成可用文字”，相应语义判据也只要求不捏造，不强制猜中 failed / noSpeech 的内部枚举。Archive 状态检查仍作为独立确定性结果保留。

修订 / 删除在模型调用前发生，所以不会引入为了验收而绕开来源屏障的 hook。发送中修订、取消重试、崩溃与旧选定来源阻断等仍由已有确定性和进程测试覆盖；不把零 admission 的确定性拒绝算成这 40 个真实模型任务之一。

## 预算与独立证据

每例只发一个正式逻辑请求，沿用 12 次模型 admission、每次最多 2,048 输出 tokens、总 120 秒的生产限制。不得为长稿或困难任务扩上限。完整 40 × 3 为 120 case-runs；保守输出上限为 2,949,120 tokens，这是限额而非使用量或费用预测，远端传输重试可能另行计费。development 24 × 3 与 holdout 16 × 3 分开执行，运行前再次确认选例、请求 / token 上限、模型及费用授权范围；当前没有为新增语料执行收费请求。

每个 repetition 使用全新 runID、工作目录、Archive、Pi 会话和 Keychain service；输出目录已存在则拒绝。固化模型、构建身份、prompt / 工具源码 hash、参数、输入与事实表 hash、来源绑定、请求时钟、所有可见 assistant 消息、所有工具参数 / 返回、保存计划正文及文件 hash、实际 token、admission、传输诊断与清理结果。重跑不能覆盖失败；同名案例的补跑独立存证，不能悄悄替换原三轮中的一次。

人工分别判 answer、plan、source support 的 pass / fail / not_evaluable；无答案的网络失败不能记语义通过。case accepted 必须同时满足机器检查、所有适用语义项通过、所有清理成功。最后按 split、分层和 repetition 汇总，并单列配对任务背景补充轮数。既有 8 × 3 的 17 通过 / 6 内容失败 / 1 网络不可评估仍是原 Debug06 的独立结果，不与后续构建合并成全通过。
