# 手表连续录音的编码开销

用户反馈满电不能持续录音 16 小时，并明确保留抬腕后的强制同步。本轮从 `3892bed` 开始，交付版本为 1.17.4。

## 代码检查与修改

`AACSegmentWriter` 每次收到音频块，都会分配转换输出缓冲；写入文件前又分配一个切片缓冲，并复制整块采样。这两次分配及第二次复制出现在连续录音的每次编码调用中。

现在每个编码器保留两个 8,192 帧缓冲。转换输出可以直接写入当前文件；只有输出跨越文件边界时，才复制对应部分到切片缓冲。转换每次开始前清空输出长度，避免短输入或结束冲刷时使用旧尾部。编码器由原来的单个串行消费任务持有，文件写入完成后才复用缓冲。

输入块仍具有独立所有权。60 秒分片、16 kHz 单声道、24 kbps AAC、完整解码检查、哈希、持久回执和中断恢复保持原有行为。

抬腕回到前台仍立即同步；标记和结束录音也继续触发同步。普通录音沿用已有的 5 分钟分批传输。编码进度仍按原频率更新，因为标记位置与故障检测也依赖它，不能把它当作纯界面刷新。波形仍独立按可见状态更新。

## 验证

- 86 项录音与同步相关测试通过，包括分片、短尾、存储不足、封口失败、中断恢复和批量传输。
- 新增用例交替输入 1、8,192、17、1,024、511 帧，覆盖 8、16、44.1、48、192 kHz 输入。核对每段帧数、起点、哈希和解码后的音频内容，检测复用缓冲时的旧数据、丢帧或重复帧。
- Mac 上对同一段 60 秒、48 kHz 音频交替运行修改前后的编码器，包含分片封口和完整性检查。每版两个进程，每进程排除首次运行，剩余 10 次的进程 CPU 时间中位数为：修改前 0.121022 秒，修改后 0.098709 秒，下降约 18.4%。测试使用共享模块的 Debug 构建与优化后的测试驱动，没有采集麦克风或进行无线传输，因此这个比例不能换算为手表整机省电比例。
- 源码 `51ac541` 的 iPhone、Watch、Widget Release 构建通过；版本、模型资源、两端签名及独立与内嵌 Watch 包一致性检查通过。

原始测试和对比记录保存在本任务 `tmp_agent_output/20261020-watch-power/`。

## 设备更新

手机覆盖安装及设备版本查询确认已更新到 1.17.4。启动时系统返回 `Locked`，未完成运行验证。安装前后资料库身份及接收诊断文件相同；诊断时间仍为本次启动尝试之前，因此只能确认容器保留，不能作为新版本同步结果。

同一脚本依次执行安装、启动和版本查询。手表安装在建立开发隧道时返回 CoreDevice 4000，底层为 RemotePairing 1001；未进入应用传输阶段，未确认腕上更新到 1.17.4。

## 续航验收

本轮读取手表进程时，开发连接返回 RemotePairing 1001，尚未获得手表 CPU 或电池消耗样本。代码中确认并减少了编码的重复工作，但尚未证明它是主要耗电来源，也未验证 16 小时续航。

真机验收应在解除充电和调试连接后持续录音，记录起止电量、时长、录音连续性、同步量及抬腕使用情况。相同条件下比较修改前后，并完成 16 小时实测；不能用 Mac 编码用时或短时设备安装结果替代。
