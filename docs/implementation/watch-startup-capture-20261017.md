# 手表启动与历史片段检查

日期：2026-10-17。代码版本：1.2.1。用户要求本轮只改代码，不编译、不安装。

## 问题与原因

手表录音主界面顶部的 `capture.status` 显示“检查已保存的片段”或“录音已中断”。前者来自历史恢复阶段，后者来自 `CaptureActivity.interrupted`。

原启动流程先校验所有历史文件、恢复编码残留，再恢复会话状态。开始与继续录音均要求整批历史恢复完成。片段积压越多，进入后等待越久。

此外，`CaptureState.restore(intent: .recording)` 将旧进程的录音状态恢复为 `interrupted`。此时采集尚未启动，界面却按旧活动状态展示“录音已中断”，没有显示中央开始入口。因此这行文字也可能只是读取了上次的状态，不能据此判断刚发生过麦克风中断。

## 代码变更

- `captureReady` 只表示必要的本机录音记录已打开。开始、继续录音与界面按钮使用它；完整历史检查完成的 `ready` 继续约束同步及持久接收确认处理。
- 旧进程未关闭的 epoch 在开放采集前登记中断。新 epoch 启动后，不再重复执行这一启动步骤。
- 用户补充：进入后需要开始录音时，中央统一显示“轻触以开始”。读取到旧录音状态、静音、采集失败或真正停止时均可点击这个入口开始或继续；仅进入前台不激活麦克风。新进程保留需要轻触启动的明确状态，迟到的系统恢复事件不能跳过它。已经在采集的运行时继续录音，仍由真实样本将状态推进为录音中。
- 历史校验在文件之间让出账本 actor，历史已确认文件按每批最多 8 个清理。让出执行权时，文件校验和数据库事务均已结束。
- 编码残留恢复可跳过仍开放的 epoch，避免把新录音的未关闭文件当作损坏残留。默认恢复接口保留原有仅恢复历史目录的行为。
- 历史恢复后的时长刷新排除当前 epoch，且核对采集 generation，避免重复计时或迟到结果覆盖新一轮采集。
- 历史检查提示移到“录音信息”，失败保留为独立的历史检查提示，正常同步不会清除它。它不替换实际录音状态、不关闭已经开放的采集按钮。读取到旧录音状态时显示“准备录音”；真正中断显示“录音暂时中断”。

## 验证边界

新增原生回归用例覆盖：暂停历史校验时启动真实麦克风；旧录音等待轻触，点击后先于历史校验完成启动；进入前台与静音会话不自动启用麦克风；历史检查失败仍能启动采集。暂停点仅控制历史任务的时序，不模拟麦克风样本。

新增录音包回归用例覆盖：AAC writer 仍持有当前文件时，历史修复不得更改、移动或隔离该 epoch 的文件；writer 关闭并登记后再恢复；时长计算排除当前 epoch。

界面回归更新静音与重开后的中央入口，并新增录音中退出、重新打开后显示“轻触以开始”的用例。
