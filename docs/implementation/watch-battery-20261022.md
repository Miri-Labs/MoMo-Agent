# 手表重复历史对账与熄屏进度通知

基线：`ea5bc1ab`。版本：1.19.8。用户反馈连续录音不足 8 小时。本轮先查安装记录、同步路径与录音回调。

## 安装与证据

此前 1.19.6 的进度通知优化未安装到手表，1.19.7 的手表安装也未成功。本轮应用版本查询和只读 DDI 检查都在建立开发通道时超时，返回 CoreDevice 4000 / RemotePairing 1001。因此尚未确认腕上实际版本，也未取得本轮 CPU 或电量样本。

以下结论来自代码与测试，不能换算为实际续航增长。下一次安装应包含此前已经合入的录音、同步与进度优化。

## 重复历史对账

抬腕调用 `foreground()`，随后请求新一轮对账。原来的查询从历史首条开始，包含已经确认、已在手表清理原音的片段。完整历史每 16 条组成一个请求；手机返回确认后，还会再次产生回执应用消息。历史越多，一次抬腕会重复核对越多已经完成的记录。

现在日常同步只核对待确认、缺失、损坏或存在回执屏障的片段。第一次核对、上一次完整核对完成已满 24 小时、系统时间回退或确认更换手机资料库后，才核对完整历史。24 小时按完整核对的完成时间计算，不增加定时唤醒；到期后的下一次同步触发完整核对。

schema 7 保存本轮范围和上次完整核对时间。进行中的请求 ID、分页范围、原音哈希与回执条件继续有效。跨天、重启或调用方式变化都先完成原有一轮，不从头重复开始。旧 schema 6 的在途请求继续按完整历史范围恢复。抬腕仍立即推进原音传输和待确认资料，不等待每日核对。

测试建立 200 个已确认并清理原音的历史片段。首次完整核对后，连续 100 次日常同步没有产生历史对账请求；新增的 17 个片段仍分两页处理，重启后沿用原请求，到期后重新检查完整历史。另覆盖回执屏障、更换接收方及旧库迁移。

## 熄屏进度

原来的主线程进度通知无论屏幕是否可见都每秒执行。现在可见时保持每秒通知；隐藏时按 60 秒采样范围合并，并在每个分片封口时通知。首次采样、抬腕和录音收尾立即交付最新位置。

编码器仍保存每次进度观察。标记、状态请求和故障检测读取最新采样位置；2 秒一次的看门狗及其故障阈值保持原样。录音采样、编码、分片保存、回执与同步批次间隔保持原样。

一小时合成输入测试中，18,000 次编码器报告全部可读。隐藏时主线程通知为 61 次，原每秒通知方案为 3,601 次，60 个分片通知均保留。测试还检查抬腕立即刷新、待处理封口标志、可见与隐藏两种状态下的短尾交付。

## 脱离调试连接后的记录

`Library/Application Support/MoMoAgent/energy-diagnostic.json` 保存最多 576 个本地样本。借用现有录音回调，每 5 分钟采样一次，正常收尾额外采样。不新增定时器，不上传原音或文字。

样本记录进程运行标识、构建号、系统时间、累计进程 CPU 时间、电量与充电状态、温度状态、界面活跃时长、当前采样帧和丢块计数，以及累计同步轮次、状态请求、状态发布、文件与控制消息完成次数和失败次数。记录在独立 actor 写入，失败只记日志，不控制采集或传输。

比较同一进程相邻样本可计算 CPU 时间增量和每小时电量变化。CPU 时间不包含系统音频服务和无线芯片的全部开销；跨进程、充电期间与开发连接期间的样本需要分开。Apple 也说明，Xcode 开发连接会影响设备睡眠观测，见 [Power Profiler](https://developer.apple.com/documentation/xcode/measuring-your-app-s-power-use-with-power-profiler)。
