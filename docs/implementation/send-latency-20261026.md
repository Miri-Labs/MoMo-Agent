## 验收口径

用户要求手机发送到收到第一段真实公开文字的时间，小于同一次模型请求首字时间 + 500ms。完整回复生成、正文进入聊天数据源、WebView 实际绘制是不同节点。三点动画、接收回执、模型 reasoning 或 heartbeat 均不算首字。

1.34.8 真机连续三条消息结果如下，**整体未达标**。不能用第二条过线代替整体验收。

| 样本 | 手机首字 | 模型请求到公开首字 | 额外开销 | 发送前能力检查 | 手机记录终态 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 第一条 | 10.295s | 3.520s | 6.775s | 5.870s | 11.510s |
| 第二条 | 3.636s | 3.148s | 0.488s | 0.001s | 9.085s |
| 第三条 | 6.048s | 3.886s | 2.162s | 1.018s | 8.222s |

这些消息由同一个常驻 Hermes 进程（PID 61795）处理，没有每条重新启动。终态记录时间不是 DOM 绘制时间。模型计时取原生 `pre_api_request` 到公开文字回调，包含模型调用的网络等待，不能称为纯模型计算时间。使用两端各自的时间差相减，不依赖两端绝对时钟同步；重试必须单独列出，不能隐藏在模型基线里。

## 修复

- 原产品消息没有注册原生 `/v1/runs/:id/events` 流。现在在原生 observer 上转发公开文字、完整消息和终态，使用 Hermes 自带的 replay cursor、流保留及鉴权；不另起模型循环。
- 拿到 admission 回执立即订阅事件，不等历史同步完成。主动发送可立即重试已经恢复的网络，仍保留服务器 429/Retry-After 与 401 阻断。
- 60 秒能力缓存过期导致发送前多一次往返。共享会话现在携带持久 inbox 的 `message_idempotency` 契约，随已验证的 assistant/instance identity 保存。原始 operation ID 和 replay deadline 仍保留；旧服务器及 legacy run 保留原能力检查。
- 服务端 input 去重记录不清理，明确承诺同一 instance 至少保留 24 小时，后续版本必须保持。资料同步和模型配置不变。
- 完整回复持久化后立即发 `message.committed`，携带与历史接口相同的消息 ID/seq。手机直接合入聊天数据源，不等 Mac 定时 projection 和手机下一轮轮询。SSE 不推进历史游标，防止跳过另一设备的并发消息；后续分页按 ID 去重并排序。没有改成逐 token 展示。
- 为首个公开 token、首个 canonical 完整消息分别记录 `firstTextReceivedAt`、`firstCommittedTextAt`，旧 journal 可解码。
- canonical 回复携带同一 run 的原始用户消息，两行原子合入；避免回复超过历史同步速度时，用户气泡先消失再出现。
- 1.34.9 首次恢复检查失败后，旧 discovery 错误会一直保留，并让新契约升级永远不再尝试。1.34.10 在后续恢复轮次重新读取契约；已经成功同步时清除过时的连接提示，新发送不等待这轮后台补查。
- 官方 Codex 的短上下文流也遵循首个有效进展的等待阶段，避免生命周期事件到达后过早触发 12 秒 idle 重试。保留显式超时设置、整体上限与正常错误语义；没有变更用户模型、代理或 reasoning 配置。
