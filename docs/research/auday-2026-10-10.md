# Auday 与 Apple 平台调研

调研日期：2026-10-10。目标：为 MoMo Agent 的手表录音、手机本地转写确定实现起点。

本轮读取 Auday 官网、FAQ、隐私政策、许可清单、中国区 App Store，以及 Apple 和模型项目的官方资料。使用浏览器复核了搜索工具遗漏的许可区块和中国区商店页面。未购买或运行 Auday，也未取得它的源码。

## 1. Auday 公开了什么

| 问题 | 公开事实 | 来源 |
| --- | --- | --- |
| 在哪里录音、转写 | Watch 采集，iPhone 接收并本地转写 | [FAQ](https://auday.ai/faq) |
| 传输节奏 | 通常约 15 分钟准备传输，实际到达受系统调度影响 | [FAQ](https://auday.ai/faq) |
| 中断后怎样处理 | 电话、Siri 等可能打断；停止后可能需要用户重新开始 | [FAQ](https://auday.ai/faq) |
| 收到后才清理吗 | 手表保留待接收录音，等待手机确认 | [FAQ](https://auday.ai/faq) |
| 支持什么语言 | 中文、英文；未提供说话人区分 | [FAQ](https://auday.ai/faq) |
| 是否有档案服务器 | 开发者声明档案保存在用户设备；可选生成式 AI 另行请求用户配置的服务 | [隐私政策](https://auday.ai/privacy) |
| 系统备份能否恢复档案 | 开发者说明其档案排除在 iCloud 和电脑设备备份之外 | [隐私政策](https://auday.ai/privacy) |

这些材料支持“手表采集、手机分批处理”的产品结构。它们没有证明 SE2 能在任意系统状态下连续录满 18 小时，也没有披露 17 Pro 的持续转写速度。

中国区商店本轮可访问。页面显示版本 1.0.1、约 630.1 MB，iPhone 要求 iOS 18.0 及以上；产品说明写配对手表需 watchOS 11 及以上。版本说明提到录音传输、状态同步和重复转写数据的改进。安装包大小不能用来推导模型运行内存。[中国区 App Store](https://apps.apple.com/cn/app/id6814210373)

官网记录的一次长时测试使用 Series 11 GPS，录制 12.5 小时。该设备与我们的 SE2 不同；本轮保留其作为产品存在性参考，不把续航结果换算到 SE2。[官网测试条件](https://auday.ai/)

## 2. 官方组件清单的准确位置

入口：[Terms → Open-source licenses](https://auday.ai/terms#open-source-licenses)。2026-10-10 的浏览器页面列出以下七项；仅靠本轮搜索工具抽取的正文会漏掉这个区块。

| 组件 | 页面指向的许可 / 版本线索 | 对 MoMo Agent 的意义 |
| --- | --- | --- |
| SenseVoiceSmall | FunASR Model License 1.1 | 可作为本地 ASR 基线，单独管理权重许可 |
| Silero VAD | MIT | 划分语音区间 |
| sherpa-onnx | Apache-2.0，链接到 v1.13.5 | 提供移动端语音推理接入 |
| ONNX Runtime | MIT，链接到 v1.27.0 | ONNX 执行引擎 |
| EmbeddingGemma | Gemma 条款 | 属于语义检索方向，首版暂缓 |
| llama.cpp / ggml | MIT，链接到 b10865 | 首版不需要对应推理路径 |
| JSON for Modern C++ | MIT | 工程依赖，不是录音转写必需的产品能力 |

许可链接中的 tag 只是可见的版本线索，不等于我们已经验证 Auday 安装包使用了这些精确构建。清单可以证明开发者披露了相关组件，不能证明它们在各设备上的调用顺序。

结合组件用途，合理推测为：iPhone 用 Silero 划分语音区间，再通过 sherpa / ONNX Runtime 调用 SenseVoice；语义检索使用另一套向量模型。**Auday 未公开上述完整调用关系**，也未公开采集 API、编码参数、量化位宽、线程数和队列实现。MoMo Agent 自行定义这些部分。

## 3. 两个不能照搬的数字与行为

官网首页展示“30 × 24 小时约 3.5 GB”；FAQ 的存储说明则以每天 8 小时、30 天约 3.5 GB 为例。两处录音时长口径不一致，不能用这个数字直接预算我们的 18 小时录音。[官网](https://auday.ai/)、[FAQ](https://auday.ai/faq)

FAQ 还说明极安静区间可能只保留时间位置。此行为与声音完整保存不同。MoMo Agent 首版先保留全部已采集音频，待真实语音漏检测试通过后，再评估静音存储优化。[FAQ](https://auday.ai/faq)

## 4. Apple 平台支持怎样的实现

| 领域 | 官方依据 | 设计结论 |
| --- | --- | --- |
| Watch 后台录音 | 归档文档说明前台开始后可以后台录音 | 采用音频会话原型，验证当前 SDK / SE2；不把后台刷新当作录音服务 |
| Watch 文件传输 | `transferFile` 在后台异步传送，系统可以限速 | 录音与传输分开，允许离线排队 |
| iPhone 收到文件 | 接收回调结束前必须移动临时文件 | 先持久保存，后转写，再按业务规则清理 |
| iPhone 后台计算 | Background Tasks 提供有限的运行机会 | 任务可暂停、可恢复，记录积压 |
| 用户启动长任务 | Continued Processing 从用户前台操作开始 | 用于用户发起的一批转写，不用于偷偷常驻 |

对应来源：[后台录音说明](https://developer.apple.com/library/archive/documentation/General/Reference/InfoPlistKeyReference/Articles/iPhoneOSKeys.html)、[文件传输](https://developer.apple.com/documentation/watchconnectivity/wcsession/transferfile(_:metadata:))、[文件接收](https://developer.apple.com/documentation/watchconnectivity/wcsessiondelegate/session(_:didreceive:))、[Background Tasks](https://developer.apple.com/documentation/backgroundtasks)、[长任务](https://developer.apple.com/documentation/backgroundtasks/performing-long-running-tasks-on-ios-and-ipados)。

`WKExtendedRuntimeSession` 的自我护理、正念、理疗、智能闹钟有各自用途和时限。它不适合作为全天录音的通用运行凭据。[Apple 扩展运行会话](https://developer.apple.com/documentation/watchkit/using-extended-runtime-sessions)

## 5. 本轮模型判断

先用 SenseVoiceSmall INT8 完成录音到文字的全流程，再用相同录音比较运行库和模型。这样可以分别定位收音、分片、VAD、识别和后台调度的问题。

- sherpa 提供 iOS 接入与 SenseVoice 示例，适合作为可复现基线。[iOS 文档](https://k2-fsa.github.io/sherpa/onnx/ios/index.html)
- 当前 SenseVoice 示例输出 token 时间，上一轮关于“只能得到整段文字”的设计应按具体版本重新核对。[模型示例](https://k2-fsa.github.io/sherpa/onnx/sense-voice/pretrained.html)
- FluidAudio 已提供 Core ML SenseVoice，但其计算设备限制必须按产物遵守。[项目说明](https://github.com/FluidInference/FluidAudio/blob/main/Documentation/ASR/SenseVoice.md)
- Apple SpeechTranscriber 支持设备内转写，可作为系统对照；中文可用性需检查真实设备和语言资产。[API 文档](https://developer.apple.com/documentation/speech/speechtranscriber)
- Paraformer 可以加入普通话对照，暂不扩展到面向用户的多模型产品。[Core ML 实现](https://github.com/FluidInference/FluidAudio/blob/main/Documentation/ASR/Paraformer.md)

没有本轮 SE2 音频和 17 Pro 运行结果，暂不把任何模型写成“iPhone 中文最好”。官方模型能力、社区移植结果与本产品实测分别记录。

## 6. 当前可决定与待验证的事项

当前可以确定：采用原生 Watch / iPhone App；使用配对设备传输；手机承担本地转写与资料存储；首版无需录音服务器。

开发前半段需要验证：后台采集稳定性、分片边界、断连补传、异常退出后恢复、腕部中文质量、手机持续计算和积压清理。设备系统版本、模型构建和音频参数必须随结果保存。

完整参数与开发顺序见[首版方案](../plan/v0.1-plan.md)。测试步骤见[真机验证计划](../plan/device-validation.md)。
