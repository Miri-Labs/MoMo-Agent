# 全天录音、持续整理与积压恢复

日期：2026-10-17。用户明确：以全天持续录音为常态，不要求结束录音才能同步、转写或查看进度。本方案覆盖旧文档中可被理解为依赖录制结束的描述。

## 决定

**新音频分片持久接收后即可触发整理。录制结束不是传输、分析、转写或每日进度的前置条件。**

采集会话、物理分片、同步批次、识别窗口和阅读段落分别建模。十小时的持续采集不产生一个十小时识别任务。epoch 是连续采样坐标系，不等于用户手动开始、结束的一轮录音；仅凭结束事件的数量不能判定异常，应结合真实停止、中断、缺片和队列进度核对。

| 用户概念 | 代码中的对象 | 它何时结束 |
| --- | --- | --- |
| 持续录音任务 | session | 用户停止或采集运行时明确结束任务；不用于卡住转写 |
| 一段连续采样坐标 | epoch | 真正的采集边界；中断、重启可能形成新坐标 |
| 一个已保存音频文件 | chunk | 约 60 秒文件封口，随后继续下一文件 |
| 一次小识别任务 | analysis window | 有足够原音及上下文即可运行和提交 |
| 昨天、今天 | 日期查询范围 | 日历划分，既不是录音任务，也不是队列的完成条件 |

结束事件只确认采样终点、帮助核对完整性和处理最后短尾。手机断连、ASR 失败、生成波形和摘要均不能阻塞手表采集。真正没有可写空间、麦克风权限失效、系统停止音频会话等情况必须明确报告，不能继续显示正常录音。

手表启动同样区分采集准备与历史检查：先读取本机录音状态并登记旧进程留下的中断，再开放新采集；历史音频校验、残留文件恢复和同步在之后继续。2026-10-17 用户补充：进入后需要开始采集时，中央统一显示“轻触以开始”，点击后启动或继续原会话；仅打开 App 或后台同步不激活麦克风。原来仍在实际采集的运行时保持录音。主界面显示实际采集状态，历史检查显示在“录音信息”中。恢复出的旧状态本身不证明刚发生了系统中断。代码及未执行验证见[手表启动修复记录](../implementation/watch-startup-capture-20261017.md)。

2026-10-17 重新核对的 [Auday FAQ](https://auday.ai/faq) 说明：通常每 15 分钟准备同步，整点、暂停或结束可提前触发；手机处理已收到的音频，执行机会受系统调度影响。它没有公开内部队列和识别窗口。以下是我们的工程决定，15 分钟不能套到 ASR 窗口。

## 持续推进的流水线

```mermaid
flowchart LR
    C[Watch 持续采样] --> F[约 60 秒分片封口落盘]
    F --> Q[持久待传队列]
    Q --> R[iPhone 保存并校验]
    R --> A[短事务登记任务和接收确认]
    A --> V[有界读取和 VAD 分析]
    V --> T[完整语音窗口逐个识别]
    T --> P[提交文字和范围进度]
    P --> I[索引及可选摘要]
    A -.持久接收确认.-> Q
    F -.持续轮换文件.-> C
```

| 环节 | 明确的规则 | 推进依据 |
| --- | --- | --- |
| 采样与封口 | 沿用约 60 秒分片，轮换文件不停止采样，采集回调仅提交有界缓冲 | 样本帧数到阈值、真实停止或中断；不读取手机处理状态 |
| 传输 | 封口即进入持久队列，按既有限流提交；断连保留并退避重试 | 连接或系统调度；系统传输完成不等于手机持久接收 |
| 接收 | 先保全文件，再校验、落库、登记处理任务及确认 outbox | 成功接收即唤醒处理；重复投递复用原身份与确认 |
| 分析 | 约两分钟输入页，保留完整分片；从已提交检查点继续 | 新输入、前台恢复、获准后台执行或明确重试；不等录制结束 |
| 识别 | 沿用最多 20 秒语音核心及前后约 300ms 上下文 | 完整核心可发布；文件边界不是句子边界 |
| 保存进度 | 静音安全位置或连续语音约 64 秒分析后发布检查点，每个识别窗口完成即提交 | 以已提交帧范围为准，未完成推理不计为处理成功 |
| 摘要 | 独立排队，读取已提交文字；时段结束后可生成该时段摘要 | 失败不回退转写、不延迟文字显示、不影响录音 |

两分钟与 64 秒是输入和进度提交边界，不是额外等待时间。模型获得输入后即可运行，自然语音结束且上下文足够时可更早提交。

## 状态与所有权

| 所有者 | 状态与合法变化 | 必须保持的区别 |
| --- | --- | --- |
| Watch 采集运行时 | 等待开始 → 采集中；真实中断 → 恢复中 → 已确认恢复/需重新开始；用户停止 → 已停止 | 手机未收到不能把采集中改成停止 |
| 双端分片账本与传输协调器 | 已封口 → 已排队 → 已提交 → 等待持久确认 → 已确认；可重试失败回到队列 | 可重放，未确认文件不能作为已送达删除 |
| 手机归档与转写协调器 | 已接收待处理 → 分析中 → 窗口待识别 → 识别中 → 已完成；另记等待输入、可重试失败、系统暂停、原音不可用 | 缺少结束事件不能把可处理范围放回等待 |

“等待输入”只用于确实缺少的帧范围，或最新语音窗口缺少右侧上下文，不能成为整轮、整天的笼统状态。已完成部分正常可读可播；其他独立录音继续处理。

`1.1.2` 在既有归档层按阶段和结构化错误码保存失败范围、次数、下次重试时间。自动处理遇到坏文件、解码或识别失败，会保留原音并继续其他独立录音；可读取原音的处理失败按 5 秒起步的指数退避，间隔上限为 5 分钟。原音不可用时等待校验通过的补传，不反复唤醒空队列。前台获得执行资格时按期限唤醒，系统暂停时停止计时；恢复后继续读取持久状态。模型与数据库错误仍明确停止并报告，不伪装成单个音频错误。取消、删除、版本修改后，失效 attempt 的迟到结果不得回写。

## 三种边界分开定义

- **真实录制终点**：只有采集端的真实停止、中断恢复记录等能确认。手机不按时间推测并写入 `epoch_closures`。
- **本次可处理范围**：当前已持久接收、连续可读的输入快照。持续录制时也能推进，不表示设备停止。
- **待补上下文的尾段**：暂不当完整核心发布，后续分片到达后继续。最多影响尾部，不能卡住前面的完整核心。

`1.1.0` 已让超过 30 分钟的旧尾按已收快照处理，明确重试也可立即处理；不写入真实结束事件，迟到音频可以继续。`1.4.0` 用 `AudioProcessingBoundary` 区分开放尾部、真实采集终点、已收快照与处理范围边界；旧 `epochClosed` 入口仅保留兼容适配，不用于生成采集结束记录。

30 分钟只作为旧尾恢复规则，不能决定何时开始分析、显示文字、计算进度或宣告整天结束。常态持续录音必须通过完全没有结束事件的回归。

## 进度与昨天的数据

每日分别显示已收到、已处理、已知待同步时长。处理进度按帧范围并集计算，分子包含已识别与确认无人声的范围；仅完成 VAD 扫描的语音不能计入已整理。

```text
已收到范围的处理进度 = 已处理音频范围 / 已持久接收音频范围
```

“昨天”只代表日历边界，不保证昨天所有文件已到手机。冻结本次已接收快照可固定批次分母；迟到文件形成新待处理范围，显示“新增收到 … 待处理”。不让正在处理的批次因新增输入百分比倒退。

已收范围处理完，显示“已整理完已收到的音频”。只有手表已封口账本和手机接收记录对齐、已知缺口解决后，才能进一步确认对应范围同步完整。手表断连或未知尾部不能变成虚假整天 100%；没有结束事件也不自动变成“资料未完成”。

| 实际条件 | 应展示的内容 |
| --- | --- |
| Watch 录音中，手机已有旧文字 | 正在录音；现有文字正常显示，新范围持续整理 |
| 已有确定待处理输入 | 百分比、已处理/已收到时长、当前阶段 |
| 最新短尾缺上下文 | 最新片段待后续音频，已完成部分保持可用 |
| 昨日已收到范围处理完，完整同步尚不确定 | 已整理完已收到的音频，同步状态另行显示 |
| 已知缺文件 | 待同步时长和缺口位置，不写等待录音结束 |
| 系统暂停处理 | 系统已暂停处理，已有进度已保存；获得执行机会后继续 |

不确定完成时间时不编 ETA。先在真实设备记录解码、VAD、ASR 的有效吞吐，再决定是否显示估计范围。

## 大量积压与资源调度

接收回调只快速持久化，不在其中执行整批 ASR、波形或摘要。数据库短事务与原生推理分离，音频逐页领取、逐窗口释放，不持有整天原音 lease，不一次解码整天 PCM。

每个模型只保留一个执行队列。`1.2.0` 将 VAD 分析与 SenseVoice 识别分为两条串行队列，普通队列最多提前分析一页；识别实例仍只有一份。低电量或明显发热时停止新增预取；后台自动处理允许电池供电，执行机会由系统安排。

`1.4.0` 按用户更新采用当日优先、历史闲时处理，覆盖原先未实施的固定 2:1 分配。分析、识别与预取共用 Archive 的自动选择器；按录制当地日期分类，最近 30 分钟的范围另有跨午夜保护。同级 epoch 通过持久轮转序号分享执行机会，每个识别窗口结束后重新比较优先级。当日没有可运行任务时，历史使用剩余执行机会；当日等待上下文、补片或退避不占住队列。历史不通过等待时间越级；新增音频长期吃满设备能力时，需要容量与吞吐测量。

同一 epoch 可按已收范围减去已分析覆盖后独立推进。新范围不修改真实 epoch 身份，核心互不重叠，仍复用现有短窗口。`analysis_epochs.checkpoint` 只表示从零开始连续覆盖的前缀；较晚范围完成不能抬高原音清理的重放下界。范围输入记忆和轮转序号随 SQLite 第 10 版迁移持久保存，失败与旧窗口身份保留。预取结果先提交再重新排队，最多保留当前批次加一页提前分析；低电量或明显发热时停止新增历史工作和预取。实现和验证边界见[调度记录](../implementation/transcription-priority-20261017.md)。

波形是低优先级派生缓存，摘要独立排队。播放和聊天先获得所需资源，不等待这些可选任务。低电量、发热、系统到期时保存检查点并暂停处理，不修改已接收原音的事实。

## 当前交付与后续顺序

代码核对结果如下，区分实际触发与仍有问题的汇总：

| 代码入口 | 当前行为 | 结论 |
| --- | --- | --- |
| `PhoneReceiveCoordinator.reconcile` → `PhoneRuntime.onChanged` | 接收收件箱后请求 `transcription.requestWork()` | 已按接收触发，不需要停止事件 |
| `TranscriptionCoordinator.drain` | 自动分析和识别统一比较日期优先级，同级 epoch 轮转；显式批次与重试保留范围 | `1.4.0`；不需要整轮结束 |
| `SpeechEngine.analyze` | 自然停顿或有界连续语音检查点产生可提交核心 | 只让未完成尾部等上下文 |
| `TranscriptionCoordinator` 的局部异常分支 | 自动处理将确定的音频错误按范围保存，跳过退避中的任务，继续领取其他任务 | `1.1.2` 实现；模型、数据库和协议错误仍走明确的全局异常分支 |
| `drain` 无任务时的汇总 | 从当前配置的持久状态区分缺片、缺上下文、原音不可用、排队和待重试 | `1.1.2` 实现；未知录制终点不决定是否已处理完已收范围 |
| `TimelineBuilder` | 根据处理、失败、待同步范围形成状态；另有 `isFinal`、`hasUnknownTail` | 未知尾部不等于未处理，阅读与同步完整性不能合并 |

验收覆盖：从未发结束事件仍连续产生结果；讲话跨文件；中间缺片而后续独立录音能处理；昨天迟到文件；上千分片；处理中到期、杀进程、重启；单文件损坏；重复接收；删除后旧结果与补传不复活；跨时区、跨午夜；后台暂停后继续；模型配置隔离。同步、处理、原音保留分别核对。
