# 录音详情页：先读懂内容，再交给助理

日期：2026-10-14。状态：已进入实现，模拟器验收进行中。

用户反馈当前详情页“完全看不懂在干嘛”。本方案依据用户截图、当前 SwiftUI 源码及原音清理契约，重排页面信息和操作。它延续已确认的黑白、系统字体和原生 Liquid Glass 方向。

## 页面在产品中的位置

MoMo Agent 的主路径是：Watch 获取现实讨论 → iPhone 转写 → 用户直接向助理派活。首页继续是聊天。用户不需要先挑选录音，助理才知道近期上下文。

录音详情是核对来源的地方。用户进入后应能回答三个问题：这是哪段录音、里面说了什么、如何回听或围绕它继续问。文件管理操作属于次要任务。

## 当前问题与改法

| 当前页面 | 用户的困惑 | 改法 |
| --- | --- | --- |
| 日期、保存状态、保留开关、导出说明先于正文 | 打开后像是在设置文件，找不到内容 | 录音时间与简短状态之后直接显示正文 |
| “原音保存在本机”下面是关闭的“保留现存原音” | 开关关着，为何还有原音；关掉会不会立即删除 | 移入原音保留设置，改为“原音不自动清理”，解释关闭后按当前天数清理 |
| 右上角只放垃圾桶 | 最明显的操作是删除 | 改为“更多”，收纳导出、原音保留、同步详情、删除 |
| “原音保留分片，不补齐缺口”“音频处理范围”常驻 | 要先理解内部存储和处理过程 | 正常时显示可理解的状态；导出限制放在导出选项中，范围明细放在详情中 |
| 每段都有“回放原音”，正文没有时间线索 | 长录音难以定位内容 | 每段显示实际时间和播放入口，正在播放的段落有清楚状态 |
| 看完正文后没有助理入口 | 无法把这段讨论接到实际任务 | 提供“围绕这段录音提问”，打开带录音引用的聊天草稿 |

## 正常状态的页面结构

下面沿用截图中的转写文本，不把疑似识别错误自行改成另一句话。示例时间和时长不表示新的录音数据。

```text
‹ 录音                                      ···

今天 05:13

转写内容

00:00                                  ▶ 回听
开饭时间早上 9 点至下午 5 点。


                  [ 围绕这段录音提问 ]
```

- 正文处于首屏主要区域。短录音保留自然留白，不为了填满屏幕添加摘要卡片或任务卡片。
- 已有正文且没有异常时，不常驻显示处理完成说明。只有转写进行中、缺少内容或发生错误时，才展示对应状态；同步明细仍可从“更多”查看。
- 录音时间按 App 当前语言显示。中文界面不混用英文日期格式。
- 标题先采用录音时间。用户可命名时显示用户名称；自动生成主题标题另行设计，不能凭一句转写猜测事件。
- 段落时间必须来自实际音频时间映射。缺少总时长时不显示虚假的完整进度条。
- 回听控件明确显示播放或停止状态。长录音按段落阅读和定位；播放器不得遮住正文。
- 播放启动后发生的异步失败也要显示在该段附近。当前页面仅显示自身操作错误，未消费播放器的异步错误状态，实施时一并接通。
- 底部“围绕这段录音提问”进入聊天草稿，附上可移除的来源引用。打开页面或点击入口都不自动发起模型请求。
- 这是一条快捷路径；首页直接派活仍自动使用已授权的近期上下文。

## 更多菜单与保留设置

“更多”包含导出、原音保留、同步与转写详情，以及末尾的删除操作。已有导出格式继续按真实能力显示，不预告尚未实现的格式。

原音保留页显示：

```text
原音不自动清理                          开关

开启后，仍保存在本机的原音不参与后续到期清理。
关闭后，原音按当前设置保留 N 天，不会立即删除。
转写文字继续保留。
```

N 读取实际设置，当前默认值为 7 天。已清理的原音不能恢复。已进入清理中的音频不能承诺取消清理，界面应显示对应状态并限制容易产生误解的切换。这个开关不是是否录音、是否保存文字或是否上传云端的开关。

删除前继续说明影响：这段录音、转写及其关联的助理资料将被清理。破坏性操作保留确认步骤。

## 状态和异常

| 实际情况 | 用户看到什么 | 可做的事 |
| --- | --- | --- |
| 当前收到的音频已转写，Watch 是否结束未知 | “已收到的内容已完成转写” | 阅读、回听、提问；不宣称已全部同步 |
| 还在转写，已有部分正文 | “正在转写，文字会继续更新” | 阅读已有正文、回听已收到的原音 |
| 系统暂停本地转写 | “回到 App 后继续转写”或真实恢复状态 | 显示可用的继续操作 |
| 已知还有音频未收到 | “还有录音未传到手机” | 查看同步详情；数量和时长仅显示已知值 |
| 分析完成但没有检测到语音 | “这段录音没有检测到说话声” | 原音可用时回听 |
| 某段转写失败 | 正文对应位置显示“这一段还没有转写成功” | 有真实重试入口时重试，其他正文继续可读 |
| 原音已清理但正文仍在 | “原音已按保留设置清理，文字仍可阅读” | 阅读和提问；不显示可用的播放按钮 |
| 资料文件发生冲突或缺失 | 明确指出受影响的资料和下一步 | 保留现有恢复能力，不能以布局精简为由藏掉阻断状态 |

正常时隐藏工程明细，异常时显示会影响阅读、播放或回答的事实。不能把“收到多少”和“处理多少相等”当成 Watch 全部同步完成。

## 实施与验收范围

第一步重排现有详情页：正文前置，文件操作移入更多，保留开关改名并解释实际效果，统一状态与日期。保留数据版本校验、删除联动、文件恢复和音频使用保护。

第二步补齐详情到聊天的来源入口。路由传递正式来源引用和版本，由现有上下文校验决定是否有效；不复制正文形成第二份事实。长段资料继续按需读取。来源过期时提示更新，不继续使用旧内容。

界面验收应独立于链路测试：第一次看到页面的人，应在数秒内找到录音内容、回听和提问入口，并能准确解释原音保留开关。覆盖短录音、长录音、转写中、部分缺失、无语音、原音已清理、大字体、VoiceOver，以及从助理来源跳入后返回会话。

原生 Liquid Glass 用于导航、菜单和底部操作层。正文保持清楚的阅读表面。设计通过的标准是任务清楚、操作可预测，不能用已调用玻璃 API 或 E2E 通过代替产品验收。

## 关联阅读页面

本次真实 Agent UI 验证还发现，保存计划页直接显示 `##`、`###`、`**` 等 Markdown 标记。计划阅读页应呈现标题、段落、列表和强调；编辑模式才展示或编辑源文本。转写原文继续按原文显示，不能为了排版或纠错而改写事实。该问题来自 `live-ui-agent-01` 的实际截图。已增加原生 Markdown 阅读组件；正文显示与原稿编辑分开，正在复测大字体和编辑流程。

参考：用户提供的当前截图、[首版方向](../design/v0.1-reference.png)、`RecordingDetailView` / `RecordingCoverageView` / `Retention` 当前实现；Apple Design 的主次、反馈和原生一致性原则。本次不采用 Mizzen 品牌资产，不增加品牌色或网页装饰。

评审采用两份独立检查：`recording_design_review` 评估产品任务和信息层级，`recording_design_evidence` 核对截图、源码与状态语义。Impeccable 的 context 和 detect 入口均因文件不可执行而失败，未取得自动检测结果。原生页面不使用浏览器覆盖层；本轮未运行视觉改版，也没有新建预览服务器。现有产品目标与截图已足够确定问题，因此本轮没有追加澄清问题。

## 当前实施

详情页已将正文与回听前置；更多菜单收纳导出、原音保留、同步详情与删除。段落时间来自采集 epoch 的墙上时钟锚点与源帧偏移；它不是对缺失音频补出的连续进度。原音不可用时保留文字并撤下对应播放按钮。中文页面采用中文日期，播放的异步失败显示在发起播放的段落旁。

提问入口只把版本化来源加入聊天草稿，用户可移除。发送后，Pi 请求保存该引用，在有界上下文中优先读取选中录音，并继续允许分段工具读取。相同请求重试保留所选来源；来源修改或删除后必须通过现有校验，不能直接使用草稿保存时的旧正文。界面没有复制一份转写内容作为新的资料真源。

已添加针对菜单、保留设置、回听、来源草稿与真实转写持久化的 UI 回归，以及段落时间/原音过期的共享测试。通过结果以实施记录为准。无语音记录目前通过详情查看范围，整段原音回听仍需单独补齐，不能把隐藏文字当作已经完成这项能力。
